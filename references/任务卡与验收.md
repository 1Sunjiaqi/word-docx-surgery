# 任务卡、验收标准与独立复核

## 1 干活卡（交给另一个会话执行时用这一段，不要写小作文）

> 在 `<worktree 路径>` 里、从 tag `<起点 tag>` 出发完成 `<任务>`；
> 只允许改 `<白名单，例如：第 17~27 张表的第 4 行"判定准则"那一格>`；
> 先做 1 处样本，把两道闸门的结论给我确认，再批量；
> 结束前给出 `docx_ledger.py` 的结论、`render_qa.py --compare` 的结论、`verify_readonly.py` 的结论；
> 每一步 commit，节点用 tag 表达。

配套：先把 `验收标准_<任务>.md` 写出来（见 `工作流.md` 第 0 节），再开工。

新工作树：`git worktree add <目录> -b task/<任务名> <起点 tag>`。

## 2 审查卡（让独立会话复核时用）

> 从 tag `<待复核 tag>` 签出一棵**新的工作树**，只做只读复核；
> 判定口径**只以** `<验收标准文件>` 为准，`<执行者自己的报告>` 只当"主张"读、不当证据；
> 逐条给出"通过 / 不通过 + 实测输出原文"；不通过项按 P0/P1/P2 排序，
> 每项给出可复现的最小命令；**不要修改任何文件**；
> 复核产物（脚本、原始输出、重渲染件）放进 `<审查目录>/`，报告原样入库。

约定（都是踩过坑总结出来的）：

- **审查者只读。** 复核报告的产物单独放一个目录，不要混进交付目录；
- **报告原样入库、不要转述。** 执行者转述复核结论会丢掉证据；
- **不移动旧 tag。** 返修往前打新 tag（`task-X-v1` → `task-X-v2`），旧节点永远可回溯；
- **返修由主会话做**，不要让审查会话顺手改（它只读）；
- 复核报告里的"我顺手杀了进程"这类副作用要单独写出来，别藏在正文里。

## 3 实验卡（拿新文档试同一套流程时用）

> 在 `<新 worktree>` 里、从 tag `<起点>` 出发做 `<任务>`；只允许改 `<白名单>`；
> 先出 1 处样本 + 两道闸门结论给我确认再批量；
> 结束前给 `docx_ledger.py` 结论和逐页渲染比对结论；每步 commit。

实验用**新工作树 + 新 tag**，这样既不影响已交付的节点，失败了直接丢弃整棵工作树。

## 4 返修单骨架（复核回来之后怎么写）

1. **复核结论**：内容可交付 / 不可交付，一句话说清；
2. **逐条判定表**：`# | 判定 | 依据（实测输出）`；
3. **必办项**，按 P0 → P1 → P2：
   - P0：结论性错误（会让交付件出错或让"验收标准"变成假话）；
   - P1：表示/工具缺陷（这次没咬到，下次会咬到）；
   - P2：文字与复现命令的出入；
   每项给出"现状复现命令 + 实测输出 + 要求"；
4. **明确不要动**：哪些数字/结构已经独立验证过、改它反而会引入风险；
5. **复现命令清单**（可直接复制执行）；
6. **返修完成的判定标准**（可执行的，不是形容词）。

## 5 交付汇报骨架

```markdown
## 做了什么
- <任务一句话>

## 机器可核对的结论
- 闸门一：<白名单条数> → <命中处数>，退出码 <0/1>
- 闸门二：页数 <a> → <b>，有变化的页 = <列表>（= 预期的那几页）
- 只读自检：<n> 个 Word 文件，退出码 <0/1>（有登记项就逐条写出）
- 产出 sha256：<...>

## 留给人判断的
- <TODO：...> / <Word 批注：...>

## 没做 / 不确定
- <...>
```

**不要出现"已完成""全部一致"这类没有数字的结论**；每个断言后面跟一条能重跑的命令。
